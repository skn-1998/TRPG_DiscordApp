## 3. アイデア全体図（クラスタ別カタログ）

各案の詳細（10 フィールド全文）は生データ参照。ここでは案名・出所・一言のみ。

### C1. Discord 構造＝マップ（8 案）

カテゴリ＝区域・チャンネル/スレッド＝場所・移動＝スレッド移動。「マップを用意する」＝「サーバーの間取りを作る」。
使い捨て部屋モデルの VTT が原理的に模倣できない一方、**正本データを Discord 構造に置くとロードマップの
リスク管理方針（正本は自前 DB・Discord は入口/投影）と衝突**する（レーン D の指摘）。全レーンの合意的解法:
正本は自前 DB の場所ノード、Discord は lazy materialization される投影。

- **チャンネル地形図**（A・推し）: 場所ノード JSON→チャンネル一括生成＋GM カード。判定→情報カードの渡済み自動記録
- **RoomTree**（B）: 場所の木＋通路。エンティティ設計と lazy materialization・customId 新設 `loc_` まで設計済み
- **ワールド・コンパイラ**（Codex R1）: シナリオ構造→Discord カテゴリ/チャンネルへの「展開」。作成専用・冪等に限定
- **ルームスレッド**（I・推し）: 1 ノード＝1 スレッド。**並行探索で GM の待ち行列を並列化**（非同期卓の律速の直撃）
- **チャンネルが部屋になる**（D・尖）: 権限ロール＝鍵。パーティ分断が構造的に解決。正本 DB 論点の出所
- **シナリオ・キット**（G）: MUD＋マダミスキット輸入。サーバーに展開できる 1 ファイル。マダミス秘密配布まで
- **Channel Cartography**（H）: 割り付け表→チャンネル生成プレビュー。既読/未読＝探索済み/未探索
- **声の地図**（C・尖）: VC＝場所。分断探索の秘匿が音響として成立。タイマン主流帯では価値が出ない懸念

### C2. 画像＋ホットスポット→スレッド（4 案）

GM が既に持つ見取り図画像にピン/領域を置き、場所ノード化してスレッドと 1:1 で結ぶ。最も直感的な「マップ先行」。
共通リスク: 画像の権利（同人シナリオ付属図）・ストレージ基盤の不在・「ココフォリアの劣化版」と見られる圧力。

- **シーンボード**（C・推し）: 領域を囲む→スレッド。「PDF とマップとココフォリアのタブ往復コピペ」を消す
- **シーン・アトラス**（Codex R1・推し）: 外部画像 URL 1 本＋ピン＋シーンカード。ピンを SceneThread とログの恒久入口に
- **フロアプラン・オーバーレイ**（A）: GM 専用準備ツールとして完結する MVP 切りで盤面非スコープ内に留める
- **間取り＝スレッド**（E・推し）: 未踏＝灰色→入ると点灯。「未知が開ける感覚」を Discord UI で起こす PL 体験の言語化

### C3. 場所シート＝テンプレ基盤の場所適用（4 案・S4 収束）

場所を sheet-engine のインスタンスにする。「テンプレを配れば卓の操作盤まで届く」（最強軸 5）が
「場所テンプレを配れば、その場所の操作盤が生える」へ 1 語替えで転写される。既存資産再利用率が全案型中最大
（テンプレ JSON・palette・判定式・±ボタン・c1 結果連動）。

- **LocationSheet**（B）: `SheetInstance.subjectKind: 'character'|'location'` の一般化。**design-v1 Phase 2/3 との順序リスク最大**。MVP は別ドメイン＋評価関数の shared 共有で先送り
- **場所シート**（J・推し）: status＝構造健全度/照度/浸食度、skill＝隠蔽度/侵入難度。禁則・幕間を後から吸収できる土台
- **間取りノート**（D・推し）: 執筆器として設計。空欄の部屋が有効な状態＝丁寧執筆と即興の両対応
- **アプローチ・マップ**（G・推し）: 区画×アプローチ（技能/難易度/成功失敗描写/警戒度）。「何を宣言していいか分からない」を消す。全案中もっとも盤面境界に近く、線引き明文化が採用条件

### C4. 情報グラフ・手がかり管理・詰み検出（7 案＋PL 面 3 案・S6/S8 収束）

空間ではなく「情報の到達可能性」をマップと呼ぶ。CoC 固有のクリュー構造（出し漏れ＝シナリオ崩壊）を
構造的に検出。共通リスク: GM の入力コストが致命的 → LLM 変換導線か既製構造の配布とセットでないと使われない。

- **クリューグラフ**（A）: 依存＋獲得経路。「崩壊の予兆が可視化される」。MVP はフラットな渡済みチェックだけ
- **ClueGraph**（B）: AcquireCondition 4 種のモデル設計。**構造化 outcome 工事（後述 F1）が前提**
- **ポイントクロール・ランナー**（C）: 到達可能性グラフ。「いま行ける場所」をボタンで出す。先行ツールの明確な空白
- **クルー・マップ**（D）: 詰み監査を**書き終わってから任意で走らせる**（常時監視しない）— 押し付け回避の運用解
- **導線リンター**（F）: publish 時 issue（error/warning 二段）。`validatePublishTemplate` の形の複製
- **確定台帳マップ**（G）: Obra Dinn 輸入。3 件セット確定で総当たり防止・未入手事実の「個数だけ」表示が探索の燃料
- **Clue Reachability**（H）: **詰みはコードで決定的に検出し、埋め方候補だけ LLM**。役割分担を機能化
- PL 面: **手がかりボード**（E・PL が線を引く）／**二重マップ**（A・「渡したのに刺さらない」の実測）／**白地図**（E・PL 作図と答え合わせ。ズレた地図は SNS に貼れる）

### C5. 舞台×シナリオ分離・配布・流通（10 案＋導線 3 案・S3 収束）

マップ（舞台）を再利用資産・配布物にし、シナリオを差し替え可能なレイヤー/差分にする。1 舞台:N シナリオ。
権利の合意的方針: **決済を持たない（SPLL の指定販売サイト制約）・シナリオ本文を保存しない・画像は参照**。

- **Stage & Overlay**（B・推し）: 二段 pin（Run→Overlay→Stage）。版管理はテンプレ v3 の解法を輸入。孤児 Beat 退避まで設計
- **StageLibrary + ScenarioBinder**（B）: 運営 seed 舞台＋外部シナリオへの**索引**（本文非保存）。準備 15 分目標
- **マップパック**（C）: 部屋 zip の Discord 版。まず JSON を貼り合う段階で価値検証
- **シナリオ・オーバーレイ**（C）: 場所は不変・レイヤーが可変。「場所は残り描写だけ空になる」引き継ぎボタン
- **ロケーション・レイヤー**（Codex R1）: MapTemplate の地点 UID を ScenarioOverlay が参照。版固定と互換規則が必須
- **付箋シナリオ**（I）: 同梱マップ 3 本＋付箋。空白から書き始める心理コストを消す
- **Scene Pack**（F・推し）: 場所ノード目録の頒布。作者に「三つ目の成果物」を要求せずルームデータの席を置き換える
- **舞台パック**（F）: BOOTH のマップ素材作者 3,000 人規模に新商材。`extends: stage@^1.0.0` の分業
- **場所ソケット規格**（Codex R2・推し）: 地図が「できること」を、シナリオが「場所の役割要求」を宣言し、GM が Binding Manifest で結線。**異なる作者の商品を素材再配布なしに組み合わせる**
- **構造は無料・本文は鍵付き**（F）: シナリオの「試着」。構造プレビュー公開＋購入者コード解錠。**法務確認なしに実装不可**
- 獲得導線: **行き先指名帳**（Codex R2・PL が地図から「行きたい」を持ち込む）／**封印地図パス**（Codex R2・PL 起点の持ち込みコード）／**地図アンソロジー・リレー**（Codex R2・地図作者が寄稿母体を公開）

### C6. 常設卓の生きた世界＝レガシー・幕間・沈殿（7 案＋卓横断 3 案・S7 収束）

マップは卓より長生きする。セッションの結末が場所に刻まれ、次のシナリオは「今の地図」の上に置かれる。
軸 2（常設卓・最強）×軸 6（ログ資産化）の合流点で、使い捨て部屋モデルには原理的に作れない。
共通リスク: **初回セッションでは何も嬉しくない**（価値が蓄積で発生）・単発卓文化が主流の CoC 圏との適合。

- **常設ワールド盤**（A）: 事件レイヤー→GM 承認分だけベースへ「焼き込み（commit）」
- **同じ町の、三年後**（D）: 版と差分＋**実測改稿**（「3 卓とも温室に行っていない」がログから出る）
- **レガシー卓マップ**（G）: 不可逆の刻印（Scar）＋条件開封の封筒＋The Quiet Year 型の PL 共同作画
- **沈殿する舞台**（F・尖）: シナリオ結末の effects が舞台を書き換え、舞台が次のシナリオを選ぶ（紐づけの向きが逆転）
- **幕間マップ**（J）: セッションとセッションの**あいだ**にだけ動く。放置した場所が悪化する
- **卓の街**（E）: Session を街の番地ピンに。**既存 DiceRollText から過去ログで自動で埋まる＝追加入力ゼロで初回価値が出る唯一の案**
- **LivingMap**（B・尖）: イベントソーシング投影。実装規模特大・認知負荷高・「マップが後から出来る」ため要望と逆向きの懸念
- 卓横断: **コモンズ・マップ**（J・尖・同一実体を複数卓で共有）／**にじむ共有世界図**（G・尖・Dark Souls の血痕＝匿名の噂だけが滲む。GM が採用しなければ存在しない）／**封緘地図**（E・尖・未通過者には墨塗り＋他卓の死亡率の濃淡だけ。PL→GM の布教装置）

### C7. 時間軸マップ（4 案・S5 収束）

行＝場所・列＝時刻の格子。NPC/怪異の行動線を引き、PC と交差したセルで遭遇が起きる。
「整合性の保持」という GM 最大の負荷を機械が肩代わり。時計は**手動進行が全レーン一致**（「ここは巻きで」が常に効く）。
共通リスク: 適合ジャンルが時限もの・クローズド・ループものに偏る（時間非依存の探索型が CoC 主流）。

- **タイムテーブル・マップ**（J）／**街の時刻表**（Codex R2・日常周期への例外としてシナリオを予約）／
  **タイムライン・マップ**（D・矛盾検出: 同時刻二重在室/死亡後の行動）／**時刻表マップ**（G・ムジュラ/Outer Wilds 輸入・ループ物正面サポート）

### C8. 場所の自動応答・KP レス・ルール改変（4 案）

場所に反応規則やルール改変を宣言し、GM を待たずにシナリオが応答する。ココフォリアの
**クリックアクション/KP レスシナリオ文化（BOOTH 流通）が市場実証**（レーン C の調査）。
共通リスク: GM の裁定権を機械が奪う → 「GM が握りつぶす/差し替える経路を常に上位に」が全レーン一致。

- **反応する舞台**（A・尖）: `on: roll(目星, success) → give: clue#3` 宣言。palette 機構の場所版。非同期で GM が寝ていても進む
- **場所が喋る**（I・尖）: 状態機械としての場所。「書けば書くほど自分が休める」報酬構造。週 1 タッチで回る卓
- **禁則マップ**（J）: 場所に紐づくのはコンテンツではなく**ルールの改変**（幸運が振れない/2 回振って悪い方）。ダイス処理フック 1 本で成立するが bcdice adapter（M4）前に作ると二重工事
- **ステージ・デッキ**（D）: 種＋ランダム表で紐づけを当日まで遅延し、出た結果を場所へ**書き戻す**（即興 KP 支援。書き戻しがなければ価値ゼロ）

### C9. ログ・実測・運行系（6 案）

マップを入力ではなく**出力先**として使う。

- **踏破ログ**（C）: セッション後に「歩いた地図」1 枚。単独スライスにしにくい（他案への寄生前提）
- **Retro-Map**（H・尖）: ログを LLM でマップ化。引用照合で幻覚検収を機械化。音声主流卓では入力が枯れる懸念
- **卓の足あと**（F）: 作者に「遊ばれ方」を返す（未回収手がかり・場所別ロール数）。まず自分のテストプレイ 1 回分から
- **記憶の地図**（I）: 復帰 5 分ブリーフィング。既読/未読を場所単位で管理
- **卓の運行盤**（I）: GM 待ち/PL 待ち/停滞◯日のカンバン。**既存チャンネルの停滞集計だけならドメイン追加ゼロで実測できる**（着手順の提案あり）
- **枝と合流**（I）: 班分けの作中時間ズレを合流点の事前設計で畳む。合流時に Bot が相互ダイジェスト配布

### C10. AI 支援層（3 案＋横断論点）

- **Room Ledger**（H・推し）: 部屋 ID 表＋「割り付け表 JSON 生成プロンプト」コピー導線（J2 の複製）。LLM コスト 0
- **Map Reader**（H）: マップ画像→部屋グラフの下書き抽出（常に下書き・GM 確定）。手入力との損益分岐が生命線
- **Session Copilot**（H）: セッション中の GM 専用 ephemeral 草案 4 枠。PL 発言由来のプロンプトインジェクション面に注意
- 横断論点（レーン H）: LLM コスト 3 択（プロンプトコピー＝J2 方式/アプリ内呼び出し/BYOK。まずコピー方式で需要を測る）・
  幻覚の 3 層検収（形式=zod/構造=グラフ検査/内容=下書き＋根拠行 ID 引用の強制で構造の幻覚に変換）・
  **原則「決定的に計算できるものを LLM にやらせない」**

### C11. 意図的逸脱・単独案

- **Map Dive Activity**（Codex R1・尖）: Discord Activity 内のライブ探索盤。「盤面では戦わない」の境界を越え始める検証用
- **恐怖気圧図**（Codex R2）: 場所を持たない非空間マップ（警察の注目/仲間内の不信/怪異への接近の圧力予報図）。`PressureContract` で結果が圧力を動かす

## 4. 横断的な設計制約・実測ファクト

コードを読んだレーン（B・H・I・Codex×2）が独立に検出した、どの案を選んでも効く制約:

- **F1. 構造化 outcome が存在しない**: `DiceExecutionService` の戻りは `{ total, details }` のみで、成功/失敗は
  details 文字列にしか現れない（critical/fumble 分類なし）。「判定成功でシナリオが進む」型の全案は
  `success|failure|critical|fumble` の構造化露出が前提工事。**c1-outcome-effects が要求する工事と同一**なので共有の足場になる
- **F2. Discord 上限 → lazy materialization 必須**: チャンネル/アクティブスレッド上限により全ノード事前生成は死ぬ。
  「開いた場所だけ実体化」を仕様の最初から書く（B）。着手時に上限の現行値を要確認
- **F3. Character の channel/thread 1:1 束縛と衝突**: 1 キャラが複数の場所を渡り歩く要求は現行 entity と正面衝突。
  「保存キーはスレッド→親チャンネルへ畳む」既存規約とも衝突し `sceneId` 相当の追加が要る（I）
- **F4. 正本は自前 DB・Discord は投影**: ロードマップの競争リスク管理（Discord 依存は UI/通知/入口に閉じる）と、
  チャンネル＝マップ案の緊張。合意的解法は「正本＝場所ノード（自前 DB）・Discord 構造＝投影」（D/B/I 一致）
- **F5. SceneThread の順序逆転**: M1 は「SceneThread は後から」と明示。マップ先行はこれを前倒しする提案なので
  **Campaign より先に Scene を作る是非は明示的な裁定が要る**（I）
- **F6. 画像基盤が存在しない**: 画像アップロードのインフラなし。ほぼ全レーンが「画像は任意添付・外部 URL・
  Discord CDN 委託」に格下げして回避。画像を正本にしない（抽象ノードが正本）は全レーン一致
- **F7. 盤面非スコープの線引き 4 項目**（B の定式化・複数レーンが同型）: (a) キャラ駒を置かない
  (b) PL は座標を動かさない (c) グリッド・距離・射線を扱わない (d) 画像は GM の準備と「今どこか」の共有のみ。
  これを仕様に明記することが画像系・アプローチ系の採用条件
- **F8. GM 裁量 3 原則**（G）: 機械は台帳係であって裁定者ではない／未登録は拒否ではなく GM へのエスカレーション／
  準備物は提案であって拘束ではない（自動発火は既定オフ）
- **F9. 権利の 3 方針**（F）: 決済を持たない（SPLL は有料 DL を指定販売サイト経由に限定 — BOOTH/TALTO と非競合の
  役割分担）／シナリオ本文をサーバーに保存しない（構造と GM 私的メモだけ）／画像は参照方式（BOOTH マップ素材の
  再配布不可規約）。※SPLL 詳細は実装検討段階で公式原文の確認必須
- **F10. M2（GM 概念・visibility）が多数案の事実上の前提**: GM 専用情報の誤露出はネタバレ事故に直結。
  M2 前に出せるのは「GM 専用準備ツールとして完結する」切り方だけ
- **F11. テンプレ v3 の設計資産が丸ごと輸入可能**: version semver・visibility 3 値・forkedFrom・publish 検証・
  JSON 貼り付け・LLM プロンプト導線・uid ベース migrate・孤児退避。第 2 の配布物の版管理を再発明しない
- **F12. 命名の期待管理**: 「マップ」と呼ぶとユーザーは絵（盤面）を期待する。抽象ノードが正本の案は
  「シーン構成」「間取り」等の命名検討が要る（B/J）

## 5. 積層モデル（ほぼ全レーンが到達した共通構造）

```
[配布・流通層]   Scene Pack / 舞台パック / ソケット規格 / 封緘・鍵付き     ← テンプレ v3 の配布モデル転用（F11）
[上位レイヤー]   手がかりグラフ / 時間軸 / 自動応答・禁則 / レガシー・幕間 / ログ出力 / PL レイヤー
[中身]           場所ごとのシーンカード or 場所シート（描写・判定・手がかり・NPC・GM メモ）
[表示形態]       (a) Discord チャンネル/スレッド投影  (b) 画像＋ホットスポット  (c) ノード図/一覧   ← 併存可・後から足せる
[土台（正本）]   場所ノード: nodeUid・名前・任意の隣接・任意の画像参照      ← S1: 12 レーン中 9 レーンの推しがここに収束
```

- 土台（場所ノード）を最初に固めれば、上は独立に足せる — が全レーン共通の結論。
- 争点は土台そのものではなく、**最初の一手でどの表示形態と中身から出すか**（＝誰を最初の顧客にするか）。
