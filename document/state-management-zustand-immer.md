# front 状態管理方針: zustand / immer の採用検討と推奨

作成: 2026-08-12（Fable）。
実測基準点: develop f7e8622e（zustand 5.0.14 と immer 11.1.16 は導入済み、使用 0）。
入力: 調査 A（現状の実測）、調査 B（技術制約と負荷評価）、追加測定 B2-plain、および本文書への 3 レンズ反証レビュー（数値転記、実コード突合、論理整合。指摘は反映済み）。
調査はいずれも read-only の独立実施で、証跡は `review-results/state-mgmt-study/`（gitignored）にある。
本文書は判断材料と推奨のみを扱い、最終判断はユーザーが行う。
決定後は design-ledger §5-2 へ転記する。

## 問いと確定済み事項

問いは「front（trpg-next-app）の標準方針として zustand / immer を使用するか」である。

確定済みで再議論しない事項:

- zustand と immer を依存として導入すること自体はユーザー決定済み（コミット 98694f5a）。本文書は使用方針だけを扱う。
- 動機はユーザー裁定で 2 点。**動機 1**：ネストした不変更新の煩雑さ。**動機 2**：状態共有と prop drilling。

## 動機 2（状態共有と prop drilling）の実需要

独立した 2 調査が同じ結論に達した。

- 調査 A: 離れたコンポーネント間で同じ状態を読むために props で運んでいる実例は 0 件。
  props の伝播は最大 2 段で、すべて直系。Context の使用も 0。
- 調査 B: 受け取って読まずに下へ渡すだけの prop は app 全体で 2 本（レイアウトの認証状態と、キャラクター一覧のクリックハンドラ）、いずれも中間コンポーネント 1 個。
  後者の終端はデバッグ用のログ出力で、実質未使用。

zustand の本領は「離れたコンポーネント間の共有」であり、その適用先が現状の front には存在しない。
page がすべて server component で、各ページが client root を 1 個だけ持つ構造が、共有の発生自体を防いでいる。

## 動機 1（ネスト更新）の所在と正体

動機 1 は実在するが、テンプレートエディタ（TemplateEditorV3.tsx）1 ファイルに局在する。
setTemplate 系の更新関数 8 本（スプレッド最深 3 段を含む）と、変数名だけが違う同型ヘルパ 2 型 × 3 本（index 一致で patch を当てる系と、index を除去して空配列を undefined に畳む系）がここに集中する。
シート編集側でネスト更新に当たるのは最深 2 段の 1 箇所だけである（反証レビューが実コードで確認）。

ただし「深いネストを 1 箇所で書いている場所」は既に存在しない。
コンポーネント分割により、深い更新は「子の 1 段 map」と「親の 2〜3 段 spread」に分散している。
したがって読者の負荷の実体は記法の煩雑さではなく、更新が 2 コンポーネントに分割されていて、子の onChange から親の実装への逆引きが要ることにある。
immer が解消するのは記法の側だけで、分割の側には効かない。

## 構造変更と immer の要因分解（負荷カウント）

代表例（3 段ネストのプール値編集）を 5 案で書き比べ、同一計測者が同一基準で負荷をカウントした。
**構造変更**とは、子から親へのコールバック連鎖を畳み、1 箇所で深く更新する形へコンポーネント API を変えることを指す。

| 指標 | A 現状 | B1 produce 差替のみ | B2-plain 構造変更のみ | B2 構造変更+immer | C zustand+immer |
|---|---|---|---|---|---|
| 前方ジャンプ | 3 | 3 | 2 | 2 | 2 |
| 逆引き | 1 | 1 | 1 | 1 | 0 |
| 変換サイト数 | 2 | 2 | 1 | 1 | 1 |
| 明示的再構築式（機械計数） | 5 | 0 | 5 | 0 | 0 |
| 同時保持数 | 7 | 8 | 7 | 5 | 5 |
| 概念数 | 6 | 8 | 5 | 5 | 9 |
| 新規 API 数 | 0 | 3 | 0 | 2 | 6 |

計数の種別には差がある。
機械計数（grep）によるのは「明示的再構築式」だけで、前方ジャンプ、逆引き、変換サイト数は明示された基準による経路トレースの導出値である。
同時保持数と概念数は同一計測者による読者シミュレーションの計数で、人による揺れが残る。

比較から読み取れることは 3 点ある。

- 構造変更（A→B2-plain）が減らすのは前方ジャンプ（3→2）、変換サイト（2→1）、概念数（6→5）である。再構築式（5 のまま）と同時保持数（7 のまま）は減らない。
- 畳んだ構造の上に immer を足す（B2-plain→B2）と、再構築式（5→0）と同時保持数（7→5）が減り、新規 API が 2 増える。
- immer を単独で足す（A→B1）と、同時保持数（7→8）と概念数（6→8）はむしろ増える。つまり immer の削減効果は畳んだ構造の上でのみ現れる。

逆引き 1 は C（zustand）でしか消えない。

補足として、4 段ネストの経路（partsKeys）では素スプレッドの再構築式は 7 個になる（式数 = 2n−1、実コードで検証済み）。
構造変更だけを行った場合、式の総数 7 は変わらず、分布が現状の 2 箇所（2 式と 5 式）から 1 箇所 7 式へ変わる。
この 4 段経路を畳んだ形の同時保持数は未測定である。

## zustand 採用時の確定コスト

採用した場合に必ず支払うことになるコストが 4 点、実測または公式文書で確認されている。

- module スコープの store は SSR でリクエスト間の値漏洩を起こす（実測。zustand 同梱 README も明示的に警告）。
  さらに本リポジトリの jest 設定には module リセットが無く、spec 間の状態汚染も実測で再現した。
  調査 B が確認した範囲では、追加規約なしで両方を防げる形は「コンポーネントが自分の store を所有する」形（createStore と Provider と useState の lazy initializer の組）であり、module スコープの store を選ぶ場合は両方を自前の規約で塞ぐ必要が生じる。
- selector が新しい参照を返すと無限レンダリングループになる（実測）。
  useShallow は 1 段しか救わず、useShallow 内で新オブジェクトを作ると警告なしでループする（実測）。
  採用時は selector 規約の整備が必須になる。
- store 更新は useTransition の非ブロッキング性を失わせる（React 公式の明文。本リポジトリでの再現は未実施）。
  useTransition は 4 ファイルで使用中で、特にシート編集クライアントは transition 内で state を更新している。
- 概念数 9 と新規 API 数 6 は全案中最大である。

固有の便益は 2 つある。
逆引きの 0 化と、古いクロージャ回避のための ref ミラー 2 本と同期 effect 1 個の削減（store.getState() が代替）である。

## immer の auto-freeze と現経路の安全性

produce は結果だけでなく、元オブジェクトから持ち越した部分木も凍結する（実測）。
server component から渡された initialTemplate の部分木が書き換え不能になり、strict mode では凍結プロパティへの代入が TypeError で落ちる。

現在の保存と検証の経路（正規化、変換、publish 検証、署名生成）は、持ち込まれた template に対しては読み取りしか行わない。
経路上に in-place の書き換えは 1 箇所あるが、対象はローカル生成した診断オブジェクトであり、持ち込まれた template ではない。
このため凍結オブジェクトを流しても全経路を通過することが決定的テストで確認されている。
ただしこの保証は現経路限定であり、今後 template への in-place 変異を書けば実行時に落ちる。
採用する場合は「エディタの template は凍結されて流れる」を規約型の不変条件として design-ledger 節 2-2 へ登録し、委譲プロンプトに明記する必要がある。

## spec の生存条件

コンポーネントの既存 spec は DOM クエリとモックした server action の引数で観測しており、app 配下の全 spec に対する機械検索でも state 実装への直接参照（renderHook、hook のスパイ、ref の取り出し）は 0 件である。
結合点は autosave の debounce 定数 import と fake timer だけで、これはどの案でも影響しない。
つまりインスタンス単位の隔離が成立する差し替えであれば、DOM 出力と autosave payload が不変である限り spec は無改変で生存する。
module スコープの store はこの条件を満たさない（spec 間の状態汚染が実測で再現している）。

## 推奨

### 推奨 1: zustand の front 標準採用は見送る

本領である動機 2 の実需要が 0 件である一方、確定コスト（概念数、selector 規約、transition の blocking 降格、store 隔離規約）は全案中最大となる。
固有の便益（逆引きの 0 化と ref ミラーの削減）はこのコストに見合わない。

再評価トリガー: 離れたコンポーネント間で同じ状態を読む実需要が実際に発生したとき。
その際は module スコープの store を採らず、コンポーネント所有の Provider 形を第一候補とする（追加規約なしで SSR 漏洩と spec 汚染を同時に防げることが確認済みの形だから）。

### 推奨 2: 「produce を既存 setState に入れるだけ」の immer 導入は不採用

実測で負荷が純増する（概念数 6→8、同時保持数 7→8。ジャンプとサイト数は不変）。
produce のカリー形と直接形が同一ファイルに混在することが増分の主因であり、動機 1 の実体（更新の 2 箇所分割）には効かない。

### 推奨 3: テンプレートエディタに限り、構造変更と immer をセットで採用する（将来スライス）

負荷カウント上の最有力案は B2（構造変更 + immer）である。
7 指標のうち新規 API 数（0→2）以外の 6 指標が現状以下になり、同時保持数を下げる案は B2 と C しかない。
C は概念数 9 と新規 API 6 を伴うため、テンプレートエディタの範囲では B2 が残る。

immer をセットにする理由は 2 つある。
第一に、immer の削減効果（再構築式 5→0、同時保持数 7→5）は畳んだ構造の上でのみ現れ、単独では負荷が純増する（推奨 2）。
第二に、構造変更だけでは再構築式 5 と同時保持数 7 がそのまま残る。

次点として、構造変更のみ（B2-plain）も成立する。
現状より悪化する指標は無く、新規 API も 0 のままで済む。
ただし 4 段経路では 1 箇所に 7 式が集まる形になり、この形の同時保持数は未測定である。
新規 API と凍結意味論の追加を避けることを優先するなら、この案を選ぶ余地がある。

適用条件（B2 を採る場合）:

- 対象はテンプレートエディタのドラフト更新ヘルパ群のみとする。
  シート編集クライアントは対象外とする。保存経路の状態がほぼすべて spec で固定された状態機械であり、ネスト更新も最深 2 段の 1 箇所しかなく、動機 1 が実在しないためである。
- produce の書き方はカリー形か直接形のどちらか 1 形に統一する（2 形態の混在が B1 の負荷増分の主因だったため）。
- 着手前に「エディタの template は凍結されて流れる」を design-ledger 節 2-2 へ登録する。

時期は急がない。
次にエディタの更新ヘルパ群を触るスライスへの同乗を既定とし、単独スライスとして先行実施するかはユーザー判断とする。

### 標準方針の文言案

front の状態管理は useState とコンポーネント分割を既定とする。
zustand は採用しない（再評価トリガー: 離れたコンポーネント間の状態共有の実需要が発生したとき）。
immer は「1 箇所で 3 段以上の不変更新を書く場面」に限定した道具として許可し、適用第 1 号はテンプレートエディタの構造改善スライスとする。
