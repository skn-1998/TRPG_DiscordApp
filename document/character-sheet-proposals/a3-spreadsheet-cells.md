# 案A3: セル参照スプレッドシート方式（Excel そのもの）

> **分類**: A系（表現モデル・排他）
> **ステータス**: 案出し（現時点では採らない想定・比較基準として記録）
> **最終更新**: 2026-07-06

## 一言でいうと

テンプレート＝「セル（名前付き or A1 参照）＋式」の自由グリッドとして、文字通り Excel を再現する案。
表現力は最大だが、**セルに意味情報がない**ため Discord 連携・検証・実装量の対価が全案中もっとも大きい。

## データモデルスケッチ

```ts
interface Sheet {
  grids: Grid[] // シート（タブ）ごとの二次元セル
  names: Record<string, CellRef> // 名前付きセル（"STR" → grid0!B2 など）
}

interface Cell {
  value?: string | number | boolean
  formula?: string // "=FLOOR((CON+SIZ)/10)" のような Excel 風式
  format?: CellFormat // 表示形式・幅・結合など
  locked?: boolean // テンプレート側で式セルを保護、入力セルのみ開放
}

// テンプレート = locked な式セル＋入力セルの構造
// キャラクター = 入力セルの値集合（テンプレートの grid への差分）
```

## 試金石: CoC の複雑ステータス

| 対象 | 表現 | 評価 |
|------|------|------|
| DEX / 半分値 / HP | 通常の式セルで自然に | ◎ |
| ダメージボーナス | VLOOKUP 相当の関数＋表領域で自然に | ◎ |
| MOV（条件分岐） | IF 関数で自然に | ◎ |
| 技能リスト | 行の複製で自然に | ◎ |

**試金石としては満点**。ただし「どのセルが技能か」「どのセルがロール対象か」をシステムは知らないため、
Discord ボタン生成には**名前付き範囲＋role 注釈**の層を別途被せる必要がある（＝結局 A2 相当のメタデータを二重に持つ）。

## 長所

- ユーザーの精神モデル（Excel）にそのまま乗れる。学習コスト実質ゼロ
- 表現の長尾に最強: 変わり種システム・自作システムでも「Excel で書けるなら書ける」
- 既存の TRPG 文化（配布されている .xlsx キャラシ）からの移植が概念的に近い

## 短所・リスク

- **意味の欠如が全てに波及**: 型検証（この列は 0〜100 など）・character ドメインへのマッピング・
  Discord 連携のいずれも、注釈レイヤーを後付けしないと成立しない
- **グリッドエディタの実装量が別格**: 自作は非現実的で、handsontable / jspreadsheet 等の外部ライブラリ導入になる
  （ライセンス・Mantine 基調 UI との不整合・バンドルサイズ）
- モバイル表示・レスポンシブがほぼ成立しない（既存フロントはモバイル対応方針）
- 自由セル数×自由式のため、評価器のサンドボックス・性能・サイズ上限の管理が最難（B1 の要求が跳ね上がる）
- 配布物（シートファイル）の検証・モデレーション（B3）も最難

## 既存資産との関係

- characterTemplate DSL・AttributeSection のどちらとも不連続。ほぼ全て新規実装になる

## 位置づけ（この案の使い方）

- 現時点では**採らない**。ただし「Excel のように」という要求の原点として、
  A1/A2/A4 が何を犠牲にしているか（自由配置・自由式・行複製）を測る基準として残す
- A2 のレイアウト / 式を強化する際の参照先とする:
  - 名前付きセル → A2 の fieldId の考え方と同じ（flat な名前空間）
  - VLOOKUP → B1 の `lookup()` 関数の UI / データ構造の参考
  - 行の複製 → repeater 仕様の参考

## もし将来この方向へ寄せるなら決めるべきこと

1. 外部グリッドライブラリの選定（ライセンス・保守性・モバイル）
2. 式方言（Excel 互換にどこまで寄せるか。IMPORT する場合の互換範囲）
3. 注釈レイヤー（named range + role）の仕様 — 実質 B4 と同じ問題に帰着する
