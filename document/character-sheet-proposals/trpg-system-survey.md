# TRPG システム横断調査 — 5セクションと AttributeValue の充足性検証

> **分類**: 調査（A/B 案の前提検証）
> **ステータス**: 調査結果（設計判断の入力）
> **最終更新**: 2026-07-06

## 目的と問い

テンプレート基盤の設計（A/B 案）に入る前提として、次の 2 つを検証する。

1. **現行の 5 セクション（status / parameter / skill / item / description）は、様々な TRPG の正本モデルとして足りるか**
2. **`AttributeValue`（name / index / values: Record<string,number> / description / dice / isVisible）の柔軟度は足りるか**

方法: 構造的に特徴のある国内外 14 系統のシステムについて「キャラクターシートに必要なデータ構造」を棚卸しし、
14 の構造パターン（P1〜P14）に正規化して現行モデルと突合する。

> 注: 本調査はシート**構造**の把握が目的。個別の数値・裁定の正確さは各ルールブックが正本であり、
> ここでの記述はデータモデル設計に必要な粒度に丸めている。

## 結論（先に要点）

- **問い1: 足りない。** 5 セクションは CoC（と類似のステータス＋パーセンタイル技能系）の形をそのまま固定したもので、
  シノビガミ・ダブルクロス・ネクロニカ・FATE 等は 5 セクションに**意味を保ったまま**収まらない。
  ただし「Discord 連携向けの materialized view」（B2 の併存戦略）としては引き続き有効。
- **問い2: 足りない。** `AttributeValue` は「合算数値（base+buff+temp…）＋単純ダイスリンク」に特化した優秀な型だが、
  文字列・真偽・選択値、複合行（武器・呪文）、タグ集合、キャラ間関係、閾値つきトラック、秘匿スコープ、
  回数リソースは**構造ごと**表現できない。A1 路線（AttributeValue の無限拡張）は god-type 化するため、
  型付きフィールドの直和（A2）＋意味ブロック（A4）路線を裏付ける結果になった。

## 検証1: 5 セクションは足りるか → **足りない**

- 5 セクションは「能力値（parameter）・可変ステータス（status）・パーセンタイル技能（skill）・所持品（item）・
  自由記述（description）」という **CoC の形の固定化**であり、上表のとおりサイコロ・フィクション系
  （特技表・秘密）、ダブルクロス（ロイス・侵蝕率）、ネクロニカ（パーツ）、FATE（アスペクト・トラック）は
  意味を保ったまま割り付けられない。「どのセクションに置くか」が決まらない＝テンプレート作者への
  規約押し付けになり、Excel 的自由の要求と正面衝突する。
- `item` は最も苦しい。AttributeSection（Record<string, AttributeValue>）では
  「武器＝命中・威力・C値・射程・備考を持つ**行**」を表現できず、description への文字列詰め込みになる。
- **ただし** 5 セクションを「Discord ロール UI 向けの投影（materialized view）」と割り切れば有効性は残る:
  ロールボタンに必要なのは skill/parameter 相当の「ラベル＋数値＋記法」だけであり、
  B4 の roll palette はまさにその一般化。**結論として「正本＝テンプレート定義セクション、
  投影＝palette（旧5セクション互換）」という B2 の二層戦略が調査でも裏付けられた**。

## 検証2: AttributeValue の柔軟度は足りるか → **足りない**

現行フィールドの監査:

| フィールド | 表現できるもの | 限界 |
|-----------|---------------|------|
| `values: Record<string, number>` | 合算数値（base+buff+temp+other…）。±操作（applyDiscordDelta）と好相性 | number 限定。文字列・真偽・選択・構造体は不可。「合算」以外の集約（最大値・個数）は不可 |
| `name` / `index` | 表示名・1次元の並び順 | 2次元配置（P6）・グルーピングは不可 |
| `description` | 自由記述 | 唯一の文字列受け皿のため、装備詳細・式・秘匿情報が全部ここへ流れ込む（phase0 §5 の二重用リスクの根） |
| `dice` | 項目に紐づく固定ダイス式 | 導出結果としてのダイス式（DB）や、状態依存の式（DX3 コンボ）は不可 |
| `isVisible` | UI 表示 on/off | 「誰に見えるか」（P10）ではない |

- 得意領域（可変数値の内訳管理と Discord ±操作）は**そのまま活かす価値がある**。
  A2/A4 でも「数値フィールドの値 = parts の合算」という意味論は Resource/Track 系に継承すべき。
- 一方で P5〜P14 は AttributeValue にフィールドを足しても解決しない（**行・集合・参照・スコープという
  「構造」の不足**であり、スカラー型の拡張では届かない）。A1（温存拡張）の天井は当初想定より低い。

## 設計案への反映（この調査で追加・修正される論点）

| 対象 | 反映内容 |
|------|---------|
| A1 | 位置づけを「A2 への第一増分・CoC 系専用」に限定強化（P5 以降が全滅のため、汎用基盤としては選べない） |
| A2 | フィールド型に **list(repeater) / track / relation / tag** を追加する必要（text〜roll だけでは P5/P7/P8/P9 が落ちる）。P12（プレイブック的合成）は showIf＋テンプレ部品化として将来枠を明記 |
| A4 | 初期ブロック候補に **RelationBlock（ロイス/絆）・TrackBlock（侵蝕率/ストレス/死亡セーヴ）** を昇格。**GridBlock（特技表）** は escape hatch では書けない専用ブロックとして別途検討（シノビガミ系の市場は大きい） |
| B1 | 基本設計は据え置きで足りる。追加論点: トラック値を式から参照（`if({erosion} >= 100, ...)`）、SW 威力表型の「多入力・振り足し表」への拡張余地 |
| B2 | 新規ドメイン論点 2 件: **キャラ間関係**（P7。参照整合・相手側からの見え方）と**共有シート**（P14。国/ギルド等の別実体）。P13 成長ログの置き場（character 内履歴 or 別コレクション） |
| B3 | 秘匿ハンドアウト（P10）は「テンプレート配布」ではなく**セッション運営機能**に属する——配布物に含めるのは「秘匿**枠**の定義」まで、という境界を明確化 |
| B4 | role 語彙の `secret` を **per-viewer スコープ（public / owner / GM）** に拡張。TrackBlock の ±/チェック操作ボタン生成を resource role に統合 |
