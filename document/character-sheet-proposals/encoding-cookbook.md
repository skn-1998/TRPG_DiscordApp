- **根拠**: design-v1.md §1-§2 の文言だけで妥当なエンコードが構築できる。根拠: (1) ListField.itemFields の型は SheetField[] 直和そのものであり ComputedField を排除していない。本仕様は禁止事項を明示列挙するスタイル（list 内 list 禁止、parts の computed/roll/text 禁止）を取っており、行内 computed が禁止リストに無い＝許可と読むのが整合的。(2) §2 の「行内式は {row.subFieldId} スコープ」という規定は、式を持てるフィールドが ComputedField のみである以上、list の itemFields に ComputedField を置けることを前提にしてはじめて意味を持つ。行内 computed が集計対象外なら {row.*} の出口が消え、構文の存在理由がなくなる。(3) sum/count の対象は「list 集計は sum count のみ」とだけあり subfield の種別制限は無い。型規則（dice は算術混入不可、sum は number）から自然に「resultType: number の ComputedField は sum 可」が導かれる。(4) 評価順序は resolvedRefs（publish 時に全参照を fieldUid へ解決した依存メタ）＋循環検出＋評価ステップ上限という §2 の規定により、単一 uid 依存グラフのトポロジカル順序として一意に決まる。「行内→集計→シート」の段階明文化が無いことは未定義を意味しない——依存が逆向きになるケースは循環検出が publish 時に拒否する。GURPS の CP 合計・WFRP/SR5e のグレード補正合計・carried フィルタ・単価×数量のいずれも lookup/if/比較/算術＋{row.*}＋sum の v1 関数セット内で完結する。仕様上の裏付けが弱い点は「集計対象の種別を明示していない」ことのみだが、これは cookbook/実装ノートで一文補えば済むレベルであり、テンプレート作者の体験を損なう awkward さは無い（判定基準に従い refuted=true に倒す）。

### R03: TrackField への式参照が現在値 number に評価されるか未規定（max アクセサ欠如・gauge 表示レンジ）

- **該当システム**: ダブルクロス3rd
- **正準エンコード**: tables:   erosion_dice: ranges [{min:0,max:59,result:0},{min:60,max:79,result:1},{min:80,max:99,result:2},{min:100,max:129,result:3},{min:130,max:159,result:4},{min:160,max:999,result:5}]（数値は例）   erosion_lv: 同型の範囲表（エフェクトLv補正）  section state（現在状態）: - erosion: TrackField { style:'gauge', max:300, parts:true,     role:{ resource:{ deltas:[+1,+2,+5,-5] } },     thresholds:[{at:60,label:'侵蝕D+1'},{at:80,label:'侵蝕D+2'},{at:100,label:'侵蝕D+3・帰還判定域'},{at:130,label:'…'}] }   // 現在値は §8-6 により mutable number → sheet.values[uid] の parts 合算が式参照 {state.erosion} の値   // thresholds は at の絶対値で発火するため max=300 でも通知は無傷 - erosion_dice: ComputedField { resultType:'number', formula:"lookup({state.erosion},'erosion_dice')" }   // lookup 不安時の等価形: if({state.erosion}>=160,5,if({state.erosion}>=130,4,if({state.erosion}>=100,3,if({state.erosion}>=80,2,if({state.erosion}>=60,1,0))))) - erosion_lv: ComputedField { resultType:'number', formula:"lookup({state.erosion},'erosion_lv')" }  section combat: - dice_pool: ComputedField { resultType:'number', formula:"{abilities.body} + {state.erosion_dice}" } - attack_mod: ScalarField(number) - attack: role: rollable { notation:"({combat.dice_pool})dx+{combat.attack_mod}", group:'戦闘' }   // Discord ± → materializer が保存時に computed と palette を再評価 → notation 内の dice_pool が現在侵蝕率へ自動追従（§4 単方向）
- **根拠**: 主張の核心は (a)「track 参照が現在値 number に評価されるか未規定」(b)「max 必須が侵蝕率の実質上限なしと衝突し gauge 表示を歪める」の 2 点だが、いずれも既存 v3 プリミティブの範囲で解消できる。  (a) 「未規定」は文言上は事実だが、意味論は既存の決着から一意に導出できる。①決着 §8-6（design-v1 §1）は parts の適用対象を「可変な number 値 —— scalar number・**track の現在値**・list 行内の number」と明記しており、track の現在値を value model 上の number として scalar number と同列に分類済み。②§3 で式評価の入力は `sheet.values`（uid キー）のみ、§4 で resource ± は field 種別を問わず `sheet.values[uid].parts.other` へ書く、と track も scalar と同一の値経路に載っている。③§2 の値型は number|text|boolean|dice の 4 つだけで構造体型が存在しないため、track フィールドが評価環境に供給できる値は parts 合算後の現在値 number 以外に型整合な解釈が**存在しない**。つまり「現在値以外に評価されうる」という競合読解が仕様上構成不可能であり、エンコードをブロックする曖昧さではない（明記は docs polish としては望ましいが、ギャップ判定の根拠にはならない）。④max アクセサ欠如も無害: max はテンプレート側の静的データ（number | {formula}）なので、式から max が要る場合は同じ式/定数を ComputedField（例 erosion_cap）に置き、track.max の formula とロール式の両方から参照すればよく、{field.max} は不要。  (b) gauge レンジ問題は表示上の好みであって構造欠落ではない。thresholds は `at` の絶対値で発火するため max=300 でも通知・resetOn・± は一切損なわれない（「全部失う」のは scalar 退避を選んだ場合のみで、その退避自体が不要）。さらに v1.1 で表示計算の正本は projection 側（DiscordProjectionViewModel / design-v1-ui.md）と定義済みなので、閾値マーカー付き gauge や 0–100 焦点帯の描画はデータ仕様を変えずレンダラ側で吸収できる。DX3 の侵蝕率が 300 を超える運用は実質なく、便宜値は安全。  閾値効果の再導出も b1 の lookup が ranges: [{min,max,result}] の範囲表と明記されているためそのまま書け、仮に不安でも if＋比較演算子の連鎖で等価に書ける。± → materializer 保存時再評価 → palette 再生成（§4 単方向）により「現在侵蝕率でコンボ式が変わる」も成立する。よって refuted=true（提案されている §2 への 1 行明記は仕様変更ではなく既定着事項の転記に相当）。
