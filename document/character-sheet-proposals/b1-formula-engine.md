# 案B1: 式・導出エンジン設計（横断）

> **分類**: B系（横断コンポーネント。A系のどれを選んでも必要）
> **ステータス**: 案出し（未決定）
> **最終更新**: 2026-07-06

## 一言でいうと

「式＝**データ**として安全に評価する」エンジンの設計。現行フロント式エンジン
（`{fieldId}` 参照・四則・max/min/floor/ceil/round・依存グラフ・循環検出。`characterTemplate/AI.types.md`）を土台に、
CoC 級の要求（**参照表・ダイス値・条件分岐**）へ拡張する。A 案の表現力の天井は実質この部品で決まる。

## 拡張の中身（現行エンジンとの差分）

1. **値の型システム**: `number | text | boolean | dice`
   - `dice` 型＝「+1d4」のような**ダイス式そのものが値**。ダメージボーナスのために必須
   - dice 値は「表示・ロール時に展開」される。算術式には直接混ぜられない
     （現行の「計算式とロールの分離ポリシー」を型システムで強制する）
2. **参照表 `lookup(式, 'tableId')`**:
   - テーブルはテンプレート内の named resource（`ranges: [{ min, max, result }]`、result は `number | dice`）
   - 例: `lookup({str} + {siz}, 'damage_bonus')` → `"+1d4"`
3. **条件 `if(cond, then, else)` ＋ 比較演算子**（`> < >= <= == !=`）: MOV・対抗優劣などに使用。
   SWITCH 相当は当面 lookup で代替できるため見送り可
4. **丸めの既定**: システムごとの既定丸め（CoC は floor）をテンプレート設定として持ち、
   除算時の暗黙丸めを明示化する
5. **集計 `sum() / count()`**: repeater / ブロック（A4）導入時に追加。それまでは見送り

## 評価器の置き場と正本

- パーサ＋AST インタープリタの**純関数**として実装（`eval` / `new Function` 禁止）
- 置き場所: TRPG-SERVER 側は `shared/`（横断純関数の単一ホーム。ARCHITECTURE の置き場所決定表に従う）。
  フロントは同一仕様の TS 実装を共有する
  - 共有方式は要検討: (a) モノレポ共有パッケージ化 / (b) 仕様書＋テストベクタを正本にした二重実装。
    (a) が理想だが、現状 2 パッケージ間のコード共有基盤がないため導入コストを見る
- **確定値の正本はサーバー評価**（保存時に評価して persist）。フロント評価はプレビューの即時再計算専用
- ダイスの実行: Discord 経路のロールは **bcdice が正本**（既存どおり）。
  シート作成時ロール（3d6×5 等）もサーバーで bcdice 実行に寄せると、記法の互換問題（フロント簡易ローラーとの差）が消える

## セキュリティ・堅牢性（式は信頼できない入力）

- 循環参照検出（フロント実装済みの依存グラフを正式仕様化）＋トポロジカル順再計算
- 上限: 式の長さ・AST ノード数・評価ステップ数・テーブル行数・フィールド数
- エラーの型: 構文エラー / 未定義参照 / 循環 / 型不一致（dice を算術に混ぜた等）/ ゼロ除算 — 作者向けに位置情報つきで返す
- 配布テンプレート（B3）の式・テーブルは他人のコードと同じ扱い。評価器の外へ出る副作用を一切持たせない

## 試金石: CoC の複雑ステータス（この部品での担保）

| 対象 | 使う拡張 |
|------|---------|
| ダメージボーナス | `lookup()` ＋ dice 値型（2 拡張の複合。**この 2 つが本設計の存在理由**） |
| 半分値/5分の1値・HP | floor（既存） |
| MOV | `if()` ＋比較演算子 |
| DEX（3d6×5） | 式エンジン外（rollOnCreate ＝ダイス実行系の仕事）。結果の格納だけ関与 |

## 決めるべきこと

1. フィールド参照の構文: flat `{dex}`（現行 DSL）か、区画付き `{parameter.dex}`（A1 のセクション構造）か
   — **A 案の選択に依存**するため、A 決定後に確定する
2. dice 値のロール結果を式へ戻すか（戻さない＝「ロールは別フィールド」原則の維持を推奨）
3. フロント / サーバーの実装共有方式（上記 (a)/(b)）
4. 関数名・記法の互換性ポリシー（bcdice 記法とテンプレート式記法の住み分けをどこで線引きするか）
