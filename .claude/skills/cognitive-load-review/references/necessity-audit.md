# リファクタ・設計提案の必要性監査（モード B 詳細手順)

大きめの構造変更提案（新しい抽象・contract 層・パターン導入・リファクタ計画の継続判断）に対して、
「本当に必要か」を 5 系統の証拠で判定する手順。SKILL.md のモード B の詳細版。

前提となる判断式:

> 構造変更の便益 = 対象の利用・変更頻度 × 実測されたタスク便益
> 構造変更のコスト = 実装工数 + **導入される認知負荷（確定・永続）**

認知負荷は返済されない固定費として満額計上する。便益側は実測値でしか見積もらない。
変更容易性の便益を主張する場合は、`review-changeability` が同一の変更シナリオで測った
変更波及・契約影響・検証/移行範囲の delta を使う。この監査は変更容易性を代行評価しない。

## 系統 1: 動機監査 — 実害はあったか

提案の動機文書（レビュー finding・設計 doc・issue）を読み、各根拠を 2 分類する:

- **実害記録**: 実際に起きた事故・バグ・手戻り・作業時間の浪費。日付・内容・コストが特定できるもの。
- **仮説リスク**: 条件付き未来形の記述。「〜を変更した際、〜すると、〜しうる」。

判定材料: 実害記録の件数。0 件なら、その提案は保険であって修繕ではない。
保険は保険料（認知負荷）との比較で判断する。

注意: 仮説リスクを無価値と断じない。破壊的操作（削除・remote 適用・課金）に関わる
仮説リスクは、発生確率が低くても影響が大きければ targeted fix（最小限の局所修正）に値する。
「大規模な構造導入」と「targeted fix」を分けて判定するのがこの監査の目的。

## 系統 2: 実ドメイン監査 — 対象は実際に変わっているか

対象コードの変更実態を実測する:

```bash
# 総変更回数
git log --oneline --follow -- <path> | wc -l
# 直近の変化
git log --since="6 months ago" --oneline -- <path>
# 高頻度で変わっているのはどこか（対象ディレクトリ内ランキング）
git log --since="6 months ago" --name-only --pretty=format: -- <dir> | sort | uniq -c | sort -rn | head -20
```

あわせて確認する:

- 予定されている機能追加・変更はあるか（roadmap・TODO・進行中ブランチ）。
- 高頻度の変更が実際にはどこで起きているか。実例: pc-config では PC/環境/profile の追加は
  JSON 編集だけで完結しており、コード本体（applySettingIni.ts）の変更は履歴 2 回だった。
  「よく変わる」のがデータなのかコードなのかを混同しない。

## 系統 3: 負荷コスト監査 — 提案は何を導入するか

提案が導入するものを数える:

- 新規行数（実装＋テスト）
- 新概念数（利用者・保守者が学ぶ型・用語・層）
- 新しい儀式（変更 1 回あたりに増える手順・照合・レビュー工程）
- 既存コードへの波及（呼び出し元の書き換え数、移行期間の二重系統）

既に部分的に実装済みの提案（作りかけの継続判断）の場合は、現物も監査する:

```bash
# export が runtime から呼ばれているか（テストを除いて数える）
grep -rn "<exportName>" --include="*.ts" | grep -v ".test.ts"
```

runtime 呼び出し 0 の export 群は、行数全体を死蔵（純コスト）として計上する。

## 系統 4: 負荷差分 — 同じ変更が楽になるのか

系統 2 で見つけた実際に起きる変更タスク（起きたことのない空想タスクではなく）を 1 つ固定し、
before / after 両方で読者シミュレーションを行う:

1. その変更を安全に行うために読むファイル・保持する前提・ホップを before 構造で数える。
2. 提案後の構造で同じ変更を行うと仮定して、同じものを数える。
3. 表にして比較する。after で「新概念の学習」が必要になる場合、それも保持数に入れる。

提案が楽にするのが「起きない変更」だけで、「起きる変更」は同じか悪化する、
というパターンが最頻の No-Go 根拠になる。

## 系統 5: steelman — 最強の擁護を先に書く

No-Go に傾いた場合ほど、判定の前に提案側の最強の擁護を誠実に 1 段落書く:

- この提案が最も価値を発揮するシナリオは何か。
- どの trigger（並列化・チーム拡大・対象ドメインの変更頻度上昇）が成立したら再評価すべきか。

steelman を書いても数字が覆らない場合のみ No-Go を出す。
覆る場合は「縮小」（targeted fix のみ実施、構造導入は trigger 付き延期）を検討する。

## 判定

| 判定 | 条件の目安 |
|---|---|
| **Go** | 実害記録あり、または実測変更頻度が高く、負荷差分表で after が明確に軽い |
| **縮小** | 本物の欠陥は数件あるが構造導入は割に合わない → targeted fix のみ実施 |
| **No-Go** | 実害記録 0 × 変更頻度低 × 負荷増。trigger を明記して封印 |

判定に含めるもの:

- 負荷差分表（SKILL.md の出力フォーマット）
- No-Go / 縮小の場合: 再評価 trigger（何が成立したら提案を再検討するか）
- 縮小の場合: targeted fix の一覧（それぞれが実害または高確度リスクに対応していること）

## 判定を歪める慣性への注意

- **sunk cost**: 「もう半分作った」「台帳がある」「handoff 文書に resume 手順がある」は
  継続の根拠にならない。作りかけの現物は系統 3 で死蔵としてカウントする側に回る。
- **レビュー由来の権威**: 「フルレビューで High 判定だった」は実害記録の代わりにならない。
  finding の本文に戻って実害/仮説を分類し直す（系統 1）。
- **完了圧力**: 「あと少しで計画完了」は回収の見込みと無関係。

## Worked example: pc-config changeability リファクタ監査（2026-07-14）

実際にこの手順で No-Go（中止・targeted fix への縮小）となった事例:

| 系統 | 実測結果 |
|---|---|
| 1. 動機 | 15 findings 中、実害記録 0 件。全て条件付き未来形 |
| 2. 実ドメイン | applySettingIni.ts の git 変更履歴 2 回。高頻度変更（PC/環境/profile 追加）は JSON のみで完結。予定された機能追加 0 |
| 3. 負荷コスト | contract 群 2,598 行＋テスト 2,230 行、runtime 呼び出し 0/166 export、新概念約 30。台帳 357KB、フェーズごとに SHA-256 receipt×3 照合の儀式 |
| 4. 負荷差分 | 実際に起きる変更（JSON への PC 追加）は before/after で変わらず。コード変更は after で新概念 30 の学習が乗る |
| 5. steelman | 「並列適用・チーム拡大時には契約が効く」→ trigger 付き延期として記録 |

判定: **縮小**。本物の欠陥 3 件（E2E_PC_APPLY 既定値・backup path 表出・CLI エラー分類）のみ
targeted fix し、contract 構造の展開は中止。
