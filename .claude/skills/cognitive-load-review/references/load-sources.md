# Extraneous 負荷源カタログ

extraneous な認知負荷の類型と、それぞれの検出ヒューリスティック・反例（これは負荷ではない）・修正方向。
finding の「類型」フィールドはこのカタログの名前を使う。
各類型の一次情報の裏取り（原典・確認内容）は `evidence.md` を参照。

## 1. 間接層（indirection without decision）

**何が負荷か**: 呼び出しを 1 ホップ辿るたびに読者は文脈をスタックに積む。
その層が何の判断もしていない（分岐しない・変換しない・守っていない）なら、
積んだ文脈は無駄になり、往復のぶんだけ保持数が増える。
依存の追跡量が認知負荷と相関することは fMRI 実証で確認されている（evidence.md S8）。

**検出**: 代表的な 1 呼び出しを端から端まで実際に辿り、各ホップで
「この層は何を決めているか」を書き出す。答えが「委譲のみ」の層を数える。
facade / wrapper / registry / manager という名前は要注意シグナル（名前だけでは断定しない）。

**反例**: 境界の安定化（外部プロセス・SSH・CDP との契約を 1 箇所に集める層）は
判断を持つ間接層であり、負荷を下げている。ホップ先で分岐・正規化・エラー変換が
行われているなら間接層 finding にしない。

**修正方向**: インライン化・層の削除。「将来差し替えるかも」は保持理由にならない
（差し替えが実際に予定されているかを確認する）。

## 2. 概念過多（concept proliferation）

**何が負荷か**: 呼び出し側が学ぶべき語彙（型・用語・層の名前・慣習）が増えるほど、
新しい読者の立ち上がりコストと、既存読者の想起コストが増える。
挙動 1 つあたりの概念数が問題であって、概念の絶対数ではない。

**検出**: 対象モジュールの export する型・関数・用語を列挙し、
「利用者が最小の正しい使い方をするために知る必要がある数」を数える。
実例の目安: pc-config contract 群は約 30 概念で、対象ドメインは setting.ini 6 キーの置換だった。

**反例**: ドメイン由来の語彙（RTCStats の各フィールド名、schtasks の概念）は intrinsic。

**修正方向**: 概念の統合・削除。層をまたいで同じ概念に別名がある場合は語彙の統一。

## 3. 死蔵（dead / unwired abstraction）

**何が負荷か**: runtime から呼ばれないコードも、読者は「これは何のためにあるのか、
消してよいのか」を考えさせられる。存在するだけで検索結果・grep・型追跡を汚す。
純粋な負のコスト。

**検出**: export ごとに呼び出し元を grep し、runtime（テスト以外）からの呼び出し数を数える。
「wiring テストが存在を強制しているだけで、本体は未接続」というパターンに注意
（テストが passing でも死蔵は死蔵）。

**反例**: 公開 API・プラグインポイントとして意図的に外部へ露出しているもの
（その意図が doc に書かれていること）。

**修正方向**: 削除。「いつか使う」は保持理由にならない。復活は git 履歴からできる。

## 4. 非局所性（action at a distance）

**何が負荷か**: ある行の正しさが、遠く離れた場所（env 変数・global 状態・別プロセス・
暗黙の実行順序・別ファイルの不変条件）に依存していると、読者はその行を見ただけでは
安全を判断できず、依存先を全部探して保持する必要がある。

**検出**: 代表変更タスクの変更点 1 箇所について「この行を壊しうるコードはどこにあるか」を
実際に探す。ファイル外・モジュール外・プロセス外にあるものを数える。
env フラグの読み取り箇所が分散している、初期化順序に暗黙の依存がある、が典型。

**反例**: 型システムが守っている依存（壊すとコンパイルエラーになる）は保持不要なので数えない。
loud fail（起動時に即死する検証）で守られている依存も同様に割り引く。

**修正方向**: 依存の局所化・読み取り箇所の一本化・型または起動時検証への昇格。

## 5. 暗黙知（obscurity）

**何が負荷か**: コードが語らないのに、知らないと壊す前提。magic number・
暗黙の前提条件・実態と乖離した名前・「なぜこの順序でないと動かないか」の欠落。

**検出**: 読者シミュレーション中に「なぜ？」と聞きたくなった箇所を記録し、
答えがコード・コメント・doc のどこにも書かれていないものを数える。

**反例**: 規約 doc・スキルに正本があるもの（読者が辿れる導線があれば暗黙知ではない）。

**修正方向**: この類型だけは「足す」修正が正しい: コメント・doc・命名改善
（→ `code-comment-rules` スキルの Why/Invariant/Boundary 分類に従う）。
構造変更で直そうとするのは過剰反応になりやすい。

## 6. 浅いモジュール（shallow module）

**何が負荷か**: インターフェースの複雑さ ≒ 実装の複雑さのモジュールは、
何も隠蔽していないのに境界の学習コストだけを課す。小さな関数・クラスへの
機械的な分割は、この類型を量産しやすい（Ousterhout はこれを classitis と呼ぶ。
深い/浅いモジュールの定義とあわせて evidence.md S4）。

**検出**: モジュールの公開面（引数・戻り値・型・呼び出し規約の総量）と、
隠している実装の複雑さを見比べる。「呼ぶより中身を読んだ/書いたほうが早い」なら浅い。

**反例**: 深いモジュール（単純な公開面の下に大きな複雑さを隠す）は分割の成功例。
関数が小さいこと自体は問題ではない。

**修正方向**: 統合してモジュールを深くする。分割の単位を「サイズ」でなく「隠蔽できる複雑さ」で選び直す。

## 7. 共有抽象結合（coupling via shared abstraction）

**何が負荷か**: 複数の呼び出し元の「たまたま似ていた」コードを 1 つの helper に
まとめると、以後どの呼び出し元の変更もその helper 越しに他の呼び出し元へ波及しうる。
読者は helper を変更するとき全呼び出し元の意図を保持する必要がある。

**検出**: helper の引数にある boolean / enum / options フラグが、実質
「呼び出し元ごとの分岐」になっていないかを見る。フラグの組み合わせのうち
実際に使われているものを数え、呼び出し元と 1:1 対応していたら結合のサイン。

**反例**: 全呼び出し元が本当に同じ意味の操作をしている共通化（意味の共通化）は正しい。
問題なのは形の共通化。

**修正方向**: 呼び出し元ごとに分割して素直に重複させる。DRY の解除は退化ではない。
誤った抽象は重複よりはるかに高くつき、対処はインライン化による重複の再導入
（Metz "The Wrong Abstraction" → evidence.md S9）。

## 8. 儀式（process ceremony）

**何が負荷か**: 認知負荷はコードの中だけにあるのではない。1 つの変更に要求される
手順・照合・レビュー工程・受け入れ儀式が重いほど、作業者が保持・確認する事項が増える。
実例: フェーズごとに SHA-256 receipt を 3 回照合する台帳運用。

**検出**: 「このモジュールに 1 行の変更を入れてマージするまでに必要な手順」を列挙して数える。

**反例**: 破壊的操作（VM 削除・remote 適用・本番接続）のガードは intrinsic。
リスクに比例した儀式は負荷ではなく安全装置。

**修正方向**: リスクと釣り合わない儀式の削除・自動化。

## 9. 語彙の不一致（inconsistent vocabulary）

**何が負荷か**: 同じ概念に層ごとに別の名前がある（または同じ名前が別概念を指す）と、
読者は対応表を頭の中で維持する必要がある。grep 可能性も壊れる。

**検出**: 代表概念を 1 つ選び、層をまたいで名前を追う（例: shop / store / tenant）。
別名の数を数える。

**修正方向**: 正本語彙を決めてリネーム。ドメイン用語 ↔ 実装用語の対応が必要な場合は
境界 1 箇所で変換し、doc に対応表を書く。
