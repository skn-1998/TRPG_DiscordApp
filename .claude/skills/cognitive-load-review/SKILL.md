# Cognitive Load Review

認知負荷を「印象」ではなく「証拠」で評価するためのスキル。
認知負荷は変更作業の人的コストに影響するが、変更容易性そのものと同義ではない。
職業開発者の作業時間の約 58% はコードの理解に費やされることが実測されており
（Xia et al. 2018）、「安全に変えるために何をどれだけ把握する必要があるか」は重要な独立軸である。

`review-changeability` は、具体的な変更シナリオに対する変更波及、影響する契約、検証・移行範囲、
副作用リスクを測る。このスキルは、概念数・ホップ数・同時保持数・暗黙知を測る。片方の結果を
もう片方の結果として報告しない。抽象化や構造変更の総合判断では、同じ代表変更について
Changeability の impact delta と Cognitive load の load delta を別々に示す。

本文の主要な主張は一次情報（原著論文・原著書籍・公式文書）で裏取り済み。
主張→出典の対応表と各原典の確認内容は `references/evidence.md` を参照。

## なぜこのスキルが必要か（実例）

このリポジトリで実際に起きたこと（2026-07、pc-config changeability リファクタ監査）:

- 変更容易性レビューの 15 findings に、実際に発生した被害の記録は **0 件**（全て条件付き未来形の仮説リスク）。
- それを動機に作られた contract 群は 2,598 行＋テスト 2,230 行、**runtime からの呼び出し 0/166 export**、新概念約 30 個。
- 対象の実ドメインは git 変更履歴 2 回のみの安定コードだった。
- 結果: 変更容易性は上がらず、認知負荷という**確定コスト**だけが残り、計画は中止された。

教訓: 構造改善の便益は、実際に起きる変更で回収できる場合に限って認知負荷の増加と比較できる。
変更波及や検証範囲の便益は `review-changeability` の実測結果を使い、このスキル内で推測しない。
仮説上の将来便益は割引いて評価し、認知負荷の増加は確定コストとして満額で計上する。
「綺麗な構造」は目的ではない。読者の負荷を下げない構造改善は、負荷を上げる改悪である。

## 測定モデル

**認知負荷 = 読者がそのコードを安全に変更するために、同時に保持しなければならない事項の量と距離。**
これは Ousterhout の複雑性 3 症状のうちの cognitive load（タスク完了のために知る必要がある量）の
操作化。人間の作業記憶は同時に約 4 チャンク（3〜5）しか保持できない（Cowan 2001）。
これを大きく超える把握を要求する構造が負荷源になる。

負荷は 2 種類に分ける（認知負荷理論: Sweller）。この区別がレビューの正確さの核心:

- **intrinsic（本質的負荷）**: ドメインそのものが要求する複雑さ（例: WebRTC 統計の意味論、SSH 越しの部分失敗）。
  除去できない。finding にしない。緩和は提示順序・コメント・doc（→ `code-comment-rules` スキル）。
- **extraneous（余分な負荷）**: 構造・書き方が読者に課している複雑さ。これだけが finding の対象。

### 5 つの計測プロキシ

指摘は必ず、以下のいずれかを**実際に数えた結果**で裏付ける:

| プロキシ | 数えるもの |
|---|---|
| 同時保持数 | 代表変更を安全に行う時点で頭に置く必要がある前提・状態・フラグの数 |
| 概念数 | 呼び出し側が学ぶ必要のある新しい語彙（型・用語・層・慣習）の数 |
| ホップ数 | 1 つの挙動を端から端まで追うのに必要なファイル/関数ジャンプの数 |
| 非局所性 | この行を壊しうるコードがどれだけ離れた場所にあるか（env・global・暗黙の順序） |
| 暗黙知 | コードが語らないのに知らないと壊す前提の数（magic value・暗黙の不変条件） |

プロキシの選定には実証的根拠がある: fMRI 実験（Peitek et al. 2021）では、分岐数
（McCabe/Cyclomatic Complexity）は認知処理と有意に相関しない一方、データフロー依存度
（DepDegree）と語彙量は脳活動・応答時間と相関した。数えるべきは分岐や行数ではなく、
依存・ホップ・概念である。

負荷源の類型カタログと検出ヒューリスティックは `references/load-sources.md` を読む。

## 証拠ルール

- すべての finding に**読者シミュレーション**を付ける: 「この変更を安全に行うには次の N 項目の
  同時把握が必要」と具体的に列挙し（file:line 付き）、カウントする。
- 「複雑に感じる」「読みにくい」「長い」だけの指摘は書かない。数えられなければ finding ではない。
- 変更頻度は必ず実測する: `git log --oneline --follow -- <path> | wc -l`、直近の変更は
  `git log --since="6 months ago" --oneline -- <path>`。「変わりそう」は根拠にならない。
- 呼び出し実態も実測する: export が runtime から呼ばれているか grep で確認する。
  テストからしか呼ばれない export は死蔵の疑い。

## モード A: コード・差分の認知負荷レビュー

1. **対象の役割と使われ方を実測で確立し、レポート冒頭に自分の言葉で書く。**
   対象が何をするものか、プロジェクト内のどこから呼ばれるか（grep で呼び出し元を実測）、
   どの実行経路・運用・テストがいつ使うのか。この理解が間違っていれば以降の finding は
   すべて間違う。先に理解を開示することで、読者はレビューの妥当性をここで検証・訂正できる。
2. **代表変更タスクを設定する。** その対象で実際に起きそうな変更を 1〜2 個選ぶ
   （git 履歴・TODO・進行中の計画から根拠を取る。空想の変更は選ばない）。
3. **読者シミュレーションを実行する。** その変更を安全に行う読者になりきり、
   読む必要のあるファイルを実際に辿り、保持事項・ホップ・概念を列挙してカウントする。
4. **intrinsic / extraneous に分類する。** intrinsic は finding にせず「除外リスト」に理由付きで記録する。
5. **extraneous のみ finding 化する。** 重大度は「負荷の大きさ × その経路の実測変更頻度」で決める。
   変更頻度がほぼゼロの場所の負荷は、原則 Low/Info に落とす。
6. **修正方向は負荷を下げるものだけ提案する。** 削除・インライン化・局所化・命名改善・コメントを優先し、
   新しい層・新しい抽象・新しい概念を足す提案は、負荷差分（before/after のカウント比較）を示せる場合のみ許す。

差分（PR）レビューの場合も同じ手順で、「この差分が導入する新概念数・追加ホップ数・
新たな非局所結合」を数える。差分が触った箇所の既存負荷は、変更頻度が高い場合のみ言及する。

対象が大きい場合は、`git log` で変更頻度の高いファイルから順にレビューする。
全ファイル網羅より、よく変わる場所の負荷を正確に測るほうが価値が高い。

**小粒度と大粒度の両方を必ず行う（片方だけで完了扱いにしない）。**

- **小粒度（ファイル内・関数内）**: 1 つの関数・1 つの差分ブロックを読む読者の保持事項・
  ホップ・命名・分岐の負荷。上の手順 3〜6 がこれにあたる。
- **大粒度（モジュール横断・アーキ）**: 機能全体を俯瞰したときの概念数と、**同じ知識が
  複数ファイルに複製されて読者に非局所追跡を強いる箇所**。役割導出・語彙・検証規則などが
  N ファイルに散っていれば、読者は「どれが正か」を毎回 grep で再構成する。
  grep で同種ロジック・同種定数・同種メッセージ生成の重複を実測し、複製数とホップ数を数える。
  この大粒度の複製は「1 本化で純減」提案になる（新抽象の追加ではない）。
  drift による変更波及の観点は `review-changeability` の再利用スイープと相補。両者の指摘が
  一致したら統合の確度が高い。

小粒度だけ見ると「各ファイルは読める」で pass にしがちだが、大粒度で見ると同じ知識の
複製が読者に非局所負荷を課している、という取りこぼしが起きる（実例: 2026-07-19 preset-map で
role 導出・slot 語彙・preset 検証が 4 ファイル複製。小粒度レビューは検出せず大粒度で判明）。

## モード B: リファクタ・設計提案の必要性判断

提案（新しい抽象・contract 層・パターン導入・大規模リファクタ）には必要性監査を行う。
モード B でもレポート冒頭に対象の役割理解（モード A 手順 1 と同じ節）を書いてから監査に入る。
詳細手順と worked example は `references/necessity-audit.md` を読む。5 系統:

1. **動機監査**: 実害の記録（起きた事故・手戻り・バグ・所要時間）はあるか。
   条件付き未来形（「〜すると〜しうる」）は仮説リスクとして明示的にラベルし、実害と混ぜない。
2. **利用実態監査**: 対象の変更頻度を git 履歴で実測し、高負荷経路に触れる頻度を確認する。
3. **負荷コスト監査**: 提案が導入する新概念数・新規行数・新しい儀式（手順・照合・レビュー工程）を数える。
4. **負荷差分**: 同一の代表変更タスクで before/after の読者シミュレーションを行い、カウントを比較する。
5. **steelman**: 判定の前に、提案側の最強の擁護を一度誠実に書く。それでも覆らない場合のみ No-Go にする。

提案が変更容易性の改善を主張する場合、その便益は `review-changeability` が同一シナリオで測った
impact delta（変更波及・契約・検証・移行範囲）を入力にする。このスキルはその値を代行評価しない。

判定は **Go / 縮小 / No-Go** の 3 値＋負荷差分表。
実害記録なし × 変更頻度低 × 負荷増、が揃ったら No-Go。
既存計画の慣性（作りかけ・台帳・handoff 文書の存在）は必要性の根拠にならない。

## 誤検出キャリブレーション

正確なレビューとは、高負荷を見逃さないことと同じくらい、負荷でないものを負荷と呼ばないこと。

- **不慣れ ≠ 認知負荷。** チームが既に知っているイディオム・規約・fixture パターンは、
  初見コストがあっても負荷源ではない。判定基準は「規約 doc・既存スキルに書かれているか」。
- **行数・関数の長さ・分岐数は負荷の代理にならない。** 長くて直線的なコードは、
  短くても間接層を挟んだコードより負荷が低いことが多い。数えるのはホップと保持数であって
  行数ではない（Cyclomatic Complexity が理解容易性を測れないことは SonarSource 白書と
  fMRI 実証の双方で確認されている → references/evidence.md S5/S8）。
- **intrinsic の複雑さを finding にしない。** WebRTC・SSH・部分失敗など、
  ドメインが要求する複雑さの除去を提案しはじめたら誤検出を疑う。
- **重複は必ずしも負荷ではない。** 共有抽象は呼び出し元同士を結合させる。
  分岐フラグだらけの共有 helper は、素直な重複 2 箇所より負荷が高い。
- **原則違反（DRY/SOLID/レイヤリング）だけでは指摘しない。** 原則は負荷の予測器にすぎない。
  カウントで裏付けられない原則違反は書かない。

## 出力フォーマット

ALWAYS use this template:

```markdown

- 実行経路: <entry point → 対象 → 依存先。呼び出し元は grep 実測（件数と代表 file:line）>
- 運用上の役割: <どの運用・テスト・CLI が、いつ・何のために使うか>

## 代表変更タスク
<実際に起きそうな変更>（根拠: git 実測 <N> 回 / <期間>）
```
