# 一次情報の出典と、台帳設計への対応

SKILL.md の [S1]〜[S4] の実体。**すべて Anthropic 公式**（engineering ブログ / Claude Code
公式ドキュメント）。`trusted-source-policy` に従い Qiita / Zenn は使用していない。

台帳の節を足す・削る・書き方を変えるときは、ここに照らして「どの原則を満たすための節か」を
言えるようにする。言えないなら、その節は装飾である。

## [S1] Effective context engineering for AI agents

- URL: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- 公開日: 2025-09-29

### 台帳の根拠になる記述

**Structured note-taking（構造化ノート）**
エージェントが context window の外に永続的なメモリを持ち、後から取り出すノートを定期的に
書く手法。Claude Code の TODO リストや `NOTES.md` が例として挙げられている。目的は複雑な
タスクをまたいで進捗・重要な文脈・依存関係を保持すること。

→ **台帳そのものの存在根拠**。台帳は「セッションを越えて残る作業メモ」の設計を、
1 ファイルの決まった節構成に固めたものである。

**Compaction（圧縮）**
context 限界が近づくと会話内容を要約し、その要約で再初期化する。高い忠実度で蒸留し、
性能劣化を最小に抑えて継続する仕組み。

→ **節 0（現在地）の根拠**。compact を跨いで生き残るのは外部ファイルだけなので、
再開に必要な状態は会話ではなく台帳側に置く。

**Sub-agent architectures（サブエージェント構成）**
専門化したサブエージェントがクリーンな context で個別タスクを扱い、主エージェントは高水準の
計画で調整する。各サブエージェントは広く探索したうえで、凝縮・蒸留された要約のみを返す
（多くは 1,000〜2,000 トークン）。

→ **作成手順 Step 2（面ごとの分担調査）の根拠**。台帳 1 本を単一の探索で書こうとせず、
面で割って要約を集めてから統合する。

**Context retrieval and agentic search（実行時取得）**
すべてを事前にロードせず、ファイルパス・保存済みクエリ・リンクといった軽量な識別子を保持し、
実行時に必要な分だけ読み込む。progressive disclosure（漸進的開示）。

→ **剪定基準の根拠**。台帳は全文を抱え込まず「引くべき場所」を指す。

**Context engineering for long-horizon tasks（長時間タスク）**
数分〜数時間に及ぶタスク（コードベース移行、調査プロジェクト）では、compaction /
structured note-taking / マルチエージェントの 3 手法を課題に応じて使い分ける。

→ **「適用しない場合」の根拠**。短い作業に台帳は要らない。

## [S2] Building effective agents

- URL: https://www.anthropic.com/engineering/building-effective-agents

### 台帳の根拠になる記述

**Workflow と Agent の区別**
ワークフローは事前に定義されたコードパスで LLM とツールを制御する。エージェントは LLM 自身が
プロセスとツール利用を動的に方向づける。

→ ループエンジニアリングは両者の中間で、**台帳が「事前に定義された部分」を担う**。
どこまでを固定し、どこから委譲先の裁量に委ねるかの線引きが台帳の設計そのものになる。

**Human-in-the-loop / 停止条件**
チェックポイントやブロッカー遭遇時に人間のフィードバックのため停止すること。制御を保つため
最大反復回数などの停止条件を設けること。サンドボックスとガードレールの下でテストすること。

→ **節 5（未決・人間の決定点）の根拠**。停止条件を走行中に発見するのでは遅いので、
台帳で事前に列挙する。

**環境からのフィードバック**
エージェントは各ステップでツール呼び出し結果やコード実行から「ground truth」を得て、
進捗を判断する。

→ **節 2-5（検収コマンド）の根拠**。実行できるコマンドが無い作業は、進捗を判定できない。

**ツール／インタフェース設計（ACI）**
ツール定義には、junior developer に向けて書くつもりの明確な説明を与える。誤用を構造的に
防ぐ（poka-yoke）。

→ **節 2-4（委譲プロンプトへの転記文）の根拠**。委譲先は文脈を共有しない読み手なので、
台帳側で誤読しようのない短文にしておく。

**複雑さへの警告**
このトレードオフが見合うかを検討すべきであり、単純な解が力尽きたときにのみ複雑さを足す。

→ **「適用しない場合」の根拠**。台帳は無料ではない。

## [S3] Best practices for Claude Code

- URL: https://code.claude.com/docs/en/best-practices
  （旧 URL `https://www.anthropic.com/engineering/claude-code-best-practices` は 308 でここへ転送）

### 台帳の根拠になる記述

**Give Claude a way to verify its work（検証手段を与える）**
実行できるチェック（テスト、ビルド、リンタ、スクリーンショット比較）を与えると、
ループが自力で閉じる。成功を主張させるのではなく、証拠（テスト出力、実行したコマンドと
その戻り、スクリーンショット）を示させる。

→ **節 2-5 の根拠**。「実在するコマンドだけを書き、1 回実行して出力を記録する」はここから。

**hooks は決定的、CLAUDE.md は助言的**
hooks は「例外なく毎回起きなければならない」処理に使う。CLAUDE.md の指示は advisory
であるのに対し hooks は deterministic である、と明確に対比されている。

→ **節 2-1 / 2-2 の分類根拠（台帳の心臓部）**。「機械で固定済み（破ると赤くなる）」と
「規約・コメント頼み（破っても全緑）」の区別は、この advisory / deterministic の対比と
同型である。後者は委譲プロンプトで名指ししない限り守られない。

**The over-specified CLAUDE.md（肥大化した指示ファイル）**
長すぎると重要なルールがノイズに埋もれ、半分が無視される。各行について
「これを消したら Claude はミスを犯すか？」と問い、否なら削る。含めるべきものと除くべきものが
表で示されており、除く側には「コードを読めば分かること」「頻繁に変わる情報」
「長い説明やチュートリアル」が挙がっている。

→ **剪定基準の根拠**。台帳は指示ファイルと同じ失敗の仕方をする。

**The trust-then-verify gap（信頼と検証の隙間）**
もっともらしい実装がエッジケースを扱えていない典型的失敗。検証できないなら出荷しない。

→ **Step 4（実測での裏取り）と節 2-5 の根拠**。

**The infinite exploration（無限探索）**
スコープを切らずに「調査して」と頼むと数百ファイルを読んで context を埋める。
狭くスコープするか、サブエージェントに逃がす。

→ **Step 1（範囲宣言）と Step 2（読み取り専用の分担）の根拠**。

**Add an adversarial review step（反証レビュー）**
新しい context のサブエージェントは差分と与えられた判定基準だけを見るため、その変更を
生んだ推論に引きずられず結果を評価できる。ただし穴を探せと指示されたレビュー担当は健全な
対象にも所見を出すため、すべてを追うと過剰設計（余計な抽象層、防御的コード、起こりえない
ケースのテスト）に向かう。正しさや要件に影響する所見だけを拾い、残りは任意扱いにする。

→ **Step 7（反証レビューと、その打ち切り基準）の根拠**。

**Manage context aggressively / compaction のカスタマイズ**
auto compaction は重要な情報を要約して残すが、何を残すかは指示で制御できる
（変更ファイル一覧やテストコマンドを必ず残す等）。

→ **節 0 と更新規律の根拠**。要約に賭けるより、外部ファイルに置くほうが確実。

**Explore first, then plan, then code**
探索と計画を実装から分離する。ただし計画にはオーバーヘッドがあり、スコープが明確で差分を
一文で説明できる小さな変更では省く。

→ 台帳作成そのものが「探索と計画」の成果物であることの根拠。同時に、小さい作業に
台帳を課さない根拠でもある。

**仕様書（SPEC）の質**
最も有用な仕様は自己完結している。関係するファイルとインタフェースを名指しし、
**何が範囲外かを述べ**、機能が動くことを証明する end-to-end の検証手順で終わる。

→ **Step 1（対象外の宣言）と節 2-5 の根拠**。

## [S4] How we built our multi-agent research system

- URL: https://www.anthropic.com/engineering/multi-agent-research-system

### 台帳の根拠になる記述

**サブエージェントへのタスク記述に必要な 4 要素**
各サブエージェントには、目的（objective）、出力形式（output format）、使うべきツールと
情報源についての指針、そして明確なタスク境界（clear task boundaries）が必要。

→ **節 2-4 と節 6 の根拠**。台帳はこの 4 要素の原材料を保持する。特に「明確なタスク境界」は
節 2-3（統合してはいけない重複）と「触らない範囲」に対応する。

**規模を問いに合わせる**
単純な問いは 1 エージェント・3〜10 ツール呼び出し、中程度は 2〜4 エージェント、
複雑な調査は責務を明確に分けた 10 以上、という配分指針が明示されている。

→ **Step 2 で面をいくつに割るかの目安**。割りすぎは失敗として名指しされている
（単純な問いに 50 エージェントを起動する例）。

**観測された失敗モード**
エージェントが作業を重複させる、隙間を残す、必要な情報を見つけられない。曖昧な指示を
サブエージェントが誤解して冗長な探索を行う。

→ **節 6（ワークキュー）を依存順で書く根拠**、および委譲文を曖昧にしない根拠。

**マルチエージェントが向かない領域**
すべてのエージェントが同じ context を共有する必要がある領域や、エージェント間の依存が多い
領域は、現状マルチエージェント向きではない。コーディングタスクは調査に比べて真に並列化
できる部分が少ない。

→ **節 6 で「並行可」を明示する根拠**。コーディングでは並行可能な範囲が狭いので、
台帳側で並行可否を判定しておく価値が高い。

**状態を持つエージェントとエラーの累積 / 再開**
エージェントは状態を持ち、エラーは累積する。最初からやり直すのは高コストなので、
中断地点から再開できる仕組みを作った。長時間タスクでは、完了したフェーズを要約し、
次に進む前に本質的な情報を外部メモリに保存する。

→ **節 0・節 3・節 4 の根拠**。「どこまで終わったか」「何が壊れていると分かっているか」を
外部に置くことが、再開コストを決める。

## 一次情報で裏付かないもの（区別して扱う）

以下は本リポジトリでの実証であって、公式一次情報ではない。台帳や委譲文で根拠として
引くときは、公式由来と混ぜず「本リポジトリの実証」と明示する。

- 委譲指示書に不変条件を書かないと、達成条件が最短経路で満たされ既存挙動が壊れる
  （memory `delegation-prompt-must-name-invariants`）
- 未検証の所見を台帳・拘束条件に昇格させると、以降のループ全体がその前提で動く
  （memory `verify-claims-before-prescribing`）
- 文書内の全セル走査（マトリクス）は文書内整合しか見ておらず、実コードとの矛盾は
  反証レビューでしか出てこない（memory `design-matrix-adversarial-pairing`）
- レビュー・調査を担当するエージェントに編集権限を渡すと作業ツリーが汚染される
  （memory `review-agents-must-be-readonly`）
