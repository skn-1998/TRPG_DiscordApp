# trpg-refactor

TRPG-SERVER のリファクタリングを「計画→委譲→検証→記録」で安全に回す統括スキル。

このスキルの肝は2つ。

**① 役割分担。** リファクタの失敗は、たいてい「コードを理解しないまま手を動かす」か「変更しただけで検証・記録を
省く」ことから来る。だからメインのあなたは手を動かす前に**コードを理解し計画を確定する司令塔**に徹し、実際の
コード変更とテストは専用スキルへ委譲する。あなたが薄く広く全部やるより、理解と検証に集中し実装は深い専用スキルに
任せる方が、速くて壊れにくい。

**② テストによる動作保証。** リファクタは「挙動を変えずに構造を変える」作業だから、**挙動が変わっていないことを
テストで証明する**のが基本。挙動に影響し得る変更は、着手前に現挙動を固定するテスト（安全網）を張り、リファクタ後に
同じテストが緑であることで動作を保証する。**動作保証テストが無いまま、挙動に影響し得る危険な変更を進めない。**

応答は日本語。コマンドは `pnpm`（npm は使わない）。

## 役割分担

- **メイン（あなた）= 司令塔**：計画書/コードを読んで理解し、計画を実コードで精緻化（行番号・深刻度・
  影響範囲・危険な変更の洗い出し）、ステップ分割、委譲プロンプト作成、サブエージェントの成果の裏取り、
  ユーザー判断の上申、AI.*.md への記録。**自分では大きな実装をしない**（小さな確認・grep・diff 確認は可）。
- **nestjs-best-practices スキル = 実装担当**：確定した変更内容をサブエージェントとして実装する。
- **test-expansion / create-test / refactor-for-testability = テスト担当**：変更箇所のテストを評価・生成する。
- **trpg-architecture スキル = 地図**：全体像・依存方向・正本ドキュメントの在り処を掴みたいとき参照。

## ワークフロー

### Phase 0: 着手前の確認（CLAUDE.md の規約）
- `TRPG-SERVER/AI.md` と、テーマに応じた `AI.*.md`（例: `AI.refactor.md`, `AI.discord.md`, `AI.test.md`）を読む。
- モジュール境界・依存方向に関わるなら `TRPG-SERVER/src/ARCHITECTURE.md` を読む（依存方向 `features → domains
  → core → shared`、`@Global`/`forwardRef` 原則禁止 などの正本）。
- 計画書がある場合（`document/*.md`, `CLAUDE_HANDOFF.md`）はそれを起点にする。

### Phase 1: コード理解と計画精緻化（ここが最重要・自分でやる）
計画書は過去の読み取りで書かれていることが多く、**行番号や深刻度が実コードとズレている**。鵜呑みにせず、
対象ファイルを実際に読んで確認・更新する。具体的には：
- 対象の行番号・現状を実コードで確認し、計画より深刻な点／既に解消済みの点を洗い出す。
- **危険な変更を事前に特定する**：その変更が外部（フロント `trpg-remix-app`、DB の既存データ、他モジュール）に
  影響しないか。例: レスポンス body のフィールド削除はフロントが依存していないか grep、暗号化鍵の変更は
  既存データの復号互換を壊さないか、等。影響があれば「やらない／別 Issue 化」を判断する。
- 設計判断は ARCHITECTURE.md の方針に合わせる（純粋層に DI を持ち込まない、循環を増やさない 等）。

### Phase 2: ステップ分割
- 各ステップを**独立コミット可能な単位**に割る。依存があれば順序を決める（例: env 必須化 → それに依存する CORS）。
- 各ステップに「変更対象・禁止事項・**動作保証テスト**・検証・完了条件」を明文化する。挙動を保つ（＝結果が
  変わらない）ことが前提のリファクタでは、「保つべき挙動を何のテストで保証するか」を先に決める。

### Phase 3: 動作保証テストを先に用意（リファクタ前の安全網）★このスキルの中核
**リファクタは「挙動を変えずに構造を変える」作業。だから挙動が変わっていないことをテストで保証する。**
挙動に影響し得る変更（フロー移設・依存差し替え・大きな分割・モジュール境界の変更 等）は、**着手前に現挙動を
固定する characterization テスト（特性化テスト）を用意し、リファクタ前のコードで緑になることを確認**してから
実装に入る。これがあるとリファクタ後に「同じテストが緑」＝挙動不変を証明でき、安心して構造を変えられる。
- テスト作成は test 系スキルへ委譲（`test-expansion` で対象選定・テスタビリティ評価 → 緑/黄は `create-test`、
  赤は `refactor-for-testability`）。「どの入力で何が呼ばれ・何を emit し・どの戻り値か」を固定し、内部実装に密結合しない。
- 自動テストが書けない/コスト過大な領域（例: 実 Discord 連携）は、最低限の手動確認手順を Phase 7 の上申に含める。
- **例外（テスト前倒し不要）**: デッドコード削除や純粋な再export整理など、build/check:circular で十分担保できる
  低リスク変更。この場合も「なぜテスト不要と判断したか」を一言記録する。

### Phase 4: 実装の委譲（nestjs-best-practices スキルへ）
ステップごとに 1 サブエージェントを起動し、`nestjs-best-practices` スキルの起動を必須化した**自己完結プロンプト**を
渡す（下記「委譲プロンプトの型」）。サブエージェントは新しい文脈で始まるので、背景・対象・禁止事項・**保つべき
挙動とそれを保証するテスト**・検証・報告形式を漏れなく書く。実装は Phase 3 のテストを**緑のまま**保つこと。

### Phase 5: テストで動作保証＋カバレッジ補強
- Phase 3 の動作保証テストがリファクタ後も**緑のまま**であることを確認する（＝挙動不変の証明）。バスやシグネチャを
  変えた場合は、テストの「呼び出し先」だけ更新し、イベント名・payload・戻り値・呼ぶ依存が**不変**であることを確かめる。
- 新たに生まれた挙動には追加テストを書く（`test-expansion`→`create-test`）。
- **既存 spec が壊れている場合**：今回の変更由来か着手前からの既存破損かを切り分ける（`git stash` でベースライン比較し、
  同一の失敗なら既存破損と確定）。新規破損ゼロを証拠付きで確認する。
- テスト負債が大きくスコープを超える場合は「変更箇所のカバレッジ回復」に絞り、残りは `AI.refactor.md`/`AI.test.md` に記録。

### Phase 6: 検証（サブエージェントの主張を自分で裏取りする）
報告を鵜呑みにせず、メインで最低限を再確認する：
- `pnpm run build`（nest build）
- `pnpm run check:circular`（madge --circular）。**UserDomain⇄AuthDomain の 1 件のみ許容**、それ以外の
  新規循環が出ていないこと。SharedModule 等を経由して循環を増やしていないか必ず確認。
- Phase 3/5 の動作保証テストを自分で実行して緑を確認。必要なら `pnpm run start:dev` で起動確認。
- `git diff` で変更範囲が想定どおりか、機密ログ等が消えたかを grep で確認。
（CLAUDE.md 規約：build 後は start:dev と check:circular を実施して依存関係を確認すること）

### Phase 7: ユーザー判断の上申
起動可否・データ互換・後方互換に影響する決定（例: env の必須化で既存環境が起動不能、鍵変更で既存データ復号不能）、
および**自動テストで担保しきれない挙動の手動確認依頼**は、勝手に決めずユーザーに選択肢を提示して確認する。

### Phase 8: 記録（AI.*.md）
CLAUDE.md 規約「作業終了後は AI.*.md に状況を必ず記載」に従う：
- `AI.refactor.md`：実施した内容・残課題・「次にやること」を更新。
- 該当ドメインの正本（例: セキュリティなら `AI.development.md` のセキュリティ節、テストなら `AI.test.md`）に追記。
  動作保証テストの内容と「次フェーズで更新すべき assert」も `AI.test.md` へ申し送る。
- コミットは**明示要求があるときだけ**行う（自動コミットしない）。要求時は独立ステップ単位で。

## 委譲プロンプトの型（nestjs-best-practices スキルへのサブエージェント指示）

```
あなたは NestJS バックエンド C:\workspace\dokcer-trpg-remix-app\TRPG-SERVER のリファクタリング実装担当です。

【最初に必須】Skill ツールで nestjs-best-practices スキルを起動し、その原則に従って実装。
応答は日本語、コマンドは pnpm。作業ディレクトリは TRPG-SERVER。

# タスク: <ステップ名（例: S1 機密ログ除去）>
<背景：なぜこの変更が必要か>

## 変更内容（ファイル:行 と before/after を厳密に）
- <ファイル:行> … <何をどう変えるか>

## やってはいけないこと（重要）
- <壊してはいけない箇所と理由。例: login レスポンスの token はフロントが依存→削除禁止>

## 保つべき挙動と動作保証テスト（重要）
- 保つべき挙動: <このリファクタで結果が変わってはいけない挙動>
- 動作保証テスト <パス>: 実装の前後で必ず実行し、**緑のまま**保つ（挙動不変の証明）。バス/シグネチャを変えた場合は
  テストの「呼び出し先」だけ更新し、イベント名・payload・戻り値・呼ぶ依存が不変であることを確認する。
- 既存破損はベースライン比較（git stash）で新規破損ゼロを確認。

## 検証（この順で実行し結果を報告）
1. pnpm run build
2. pnpm run test <動作保証テスト/関連spec>（緑のまま保つ）
3. pnpm run check:circular（UserDomain⇄AuthDomain のみ許容・新規循環なし）
4. git diff --stat で変更範囲が想定内か確認

## 報告フォーマット
- 変更箇所の before/after 要約
- build / test / check:circular の結果（失敗ならエラー全文）
- 守った禁止事項の確認
- 予期せず詰まった点

コミットはしないでください（メインが後でまとめて行う）。
```

ポイント：①スキル起動を必須化、②変更対象だけでなく**禁止事項**を明示、③検証コマンドと**報告フォーマット**を
固定、④コミット禁止。これで成果が均質になり、裏取りしやすくなる。

## やらないこと
- コードを理解せずに委譲しない。計画書の行番号を実コードで確認せずに渡さない。
- サブエージェントの「build 成功」報告を鵜呑みにしない。最低限メインで build/check:circular を再実行する。
- 1 つのサブエージェントに無関係な複数ステップを詰め込まない（独立コミット単位で分ける）。
- **挙動に影響し得るリファクタを、動作保証テスト（安全網）無しで進めない。** 低リスクで省く場合は理由を記録する。
- スコープ外のテスト負債や型負債まで巻き込まない。見つけたら記録し別タスク化する。
- 自動コミットしない。挙動を変える変更を「テスト追加のため」に紛れ込ませない。
- フロント（trpg-remix-app）の改修が必要な変更を、影響確認なしに進めない。
